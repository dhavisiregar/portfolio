# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start the Vite dev server with HMR
- `npm run build` — production build to `dist/`
- `npm run preview` — serve the production build locally
- `npm run lint` — run ESLint over the whole project (flat config, `eslint.config.js`)

There is no test suite and no test runner configured in this project. [.github/workflows/ci.yml](.github/workflows/ci.yml) runs `npm run lint` and `npm run build` on every push/PR to `main` (Node 20) — keep both passing locally before pushing, since there's no test suite to catch regressions otherwise.

## Architecture

This is a single-page personal portfolio built with React 18 + Vite, styled with Tailwind CSS, and animated with `framer-motion`. There is no router — the page is one long scroll of `<section>`s assembled in [App.jsx](src/App.jsx), each corresponding to a component in `src/components/`: `Navbar`, `Hero`, `About`, `Tech`, `Experience`, `Projects`, `Contact`. Sections are anchored by `id` (`#about`, `#technologies`, `#experience`, `#projects`, `#contact`) and `Navbar.jsx` scroll-spies these ids (via `IntersectionObserver`/scroll handlers) to highlight the active nav link and drive a scroll-progress indicator.

**Language (ID/EN)**: [src/i18n/LanguageContext.jsx](src/i18n/LanguageContext.jsx) is a hand-rolled i18n layer (no library — chosen over react-i18next to keep bundle size down for just 2 static languages) — `LanguageProvider` (wraps the app in `App.jsx`) holds `language` (`"id"` default, persisted to `localStorage`) and `toggleLanguage`; `useTranslate()` returns a `t()` function that resolves a bilingual field for the current language. Bilingual data is a plain `{ id, en }` object (or `{ id: fn, en: fn }` for aria-labels that need interpolation in language-correct word order, e.g. `UI_TEXT.nav.visitProfileAria`) — call `t(field)` or `t(field, ...args)` for the function form. `HERO_CONTENT`, `ABOUT_TEXT`, `EXPERIENCES[].year`/`.description`, and every `PROJECTS[].description`/`longDescription`/`problemStatement`/`challenges` are bilingual this way; `role`, `company`, project `title`/`technologies`, and `CONTACT` fields are deliberately left as plain strings (proper nouns / conventionally-English job titles/tech jargon that don't change between languages). All UI chrome text (nav labels, buttons, form copy, aria-labels) lives in `UI_TEXT` in `constants/index.js`, grouped by component. When adding a new user-facing string anywhere, add it to `UI_TEXT` (or make the constant bilingual) rather than hardcoding literal text in JSX — a stray hardcoded string silently won't switch languages.

**Content vs. code split**: all content data lives in [src/constants/index.js](src/constants/index.js) as named exports — `HERO_CONTENT`, `ABOUT_TEXT`, `EXPERIENCES`, `CONTACT`, `PROJECTS`, `TECH_STACK`, `UI_TEXT` — imported by the matching component (`Projects.jsx`, `Tech.jsx`, etc.). Most long-form fields are bilingual `{ id, en }` objects, not plain strings — resolve them with `t()` from `useTranslate()` (see Language below) rather than rendering the object directly. `PROJECTS` entries carry a resolved `images` array (from the `images` asset map, see below; first entry is the card thumbnail, more entries enable the modal carousel) and `TECH_STACK` entries carry the actual `react-icons` component reference as `icon` plus a `color` className, so this file also imports those icon components and `images` — it's a data file, not a plain-strings-only file. When updating resume/bio copy, adding a project card, or adding a tech icon, edit `constants/index.js`; components should stay presentation-only. **`TECH_STACK[].color` gotcha**: most entries use a literal brand hex (`text-[#3178c6]` etc.) which is safe in both themes, but a genuinely monochrome logo (no real brand hue — Next.js, Filament, Express, Prisma) must use `text-fg`, never a hardcoded `text-white`/`text-black` — the icon sits on `bg-surface-raised`, which is dark in dark mode and near-white in light mode, so a fixed white/black icon disappears entirely in one of the two themes. This exact bug shipped once (all three "text-white" icons went invisible in light mode) before being caught and fixed.

**Project detail modal**: each `PROJECTS` entry also carries `longDescription`, `problemStatement`, `challenges` (render only if truthy — omit/set falsy to hide that section), `repoLink` (`null` hides the GitHub button), and `link` (`null` hides the "Live Demo" button too, showing `UI_TEXT.modal.noLiveDemo` instead — for a genuinely internal-only project like `id: 11` Budget Controller, both `link` and `repoLink` are `null`). Clicking a card in [Projects.jsx](src/components/Projects.jsx) opens [ProjectModal.jsx](src/components/ProjectModal.jsx) (rendered via `AnimatePresence`); the modal owns its own body-scroll lock, Escape-to-close, backdrop-click-to-close, and a manual focus trap (queries focusable elements on each Tab press rather than a library) — cards no longer link out directly, all outbound links (`link`/`repoLink`) live inside the modal.

**Project status badge**: `PROJECTS.status` (`"live"` / `"offline"` / `"n/a"`) drives the small badge on each card in `Projects.jsx` (`STATUS_BADGE` map). This is **manual, not an automated uptime check** — deliberately, after weighing the options with the user: a real client-side check either needs a third-party service (no reliable free one identified) or a `no-cors` reachability probe, which risks a false "Offline" reading whenever a visitor's ad-blocker/firewall blocks the target domain — a worse failure mode for a portfolio than a status the owner updates by hand. Flip a project's `status` yourself when a demo goes down.

**"Download CV"**: the button in [Hero.jsx](src/components/Hero.jsx) is a plain `<a href="/CV.pdf" download>` pointing at the static `public/CV.pdf` the user maintains by hand — it is **not** generated from `constants/index.js`. (An earlier iteration auto-built a resume from `EXPERIENCES`/`PROJECTS`/etc. via `window.print()`; it was replaced with this static file by explicit request once the user had their own polished CV ready.) This means `public/CV.pdf` needs to be manually re-exported and replaced whenever `EXPERIENCES`/`PROJECTS`/`ABOUT_TEXT` changes — it will silently go stale otherwise, since nothing enforces the two staying in sync.

**Asset manifest**: `src/assets/index.js` uses Vite's `import.meta.glob("./*.{png,jpg,jpeg,svg,webp,gif}", { eager: true })` to auto-discover every image in `src/assets/` and exports it as `images["filename.ext"] -> resolved URL`. Dropping a new file into `src/assets/` makes it available via `images["new-file.png"]` immediately, no import statement needed — but it also means *every* file physically present in that folder gets eagerly bundled into the production build whether or not any component references it, so don't leave stray/unused images there.

Project screenshots and profile photos are stored as `.webp`, pre-resized to roughly their max display size (project thumbnails ~640px wide, profile photos ~800-900px wide) rather than the original camera/screenshot resolution — keep new images in that ballpark instead of dropping full-resolution PNGs/JPEGs in. Hero/Navbar/About `<img>`/`<m.img>` tags carry explicit `width`/`height` matching the file's actual pixel dimensions (for aspect-ratio/CLS purposes) — update those if you swap in an image with different dimensions. Project cards in `Projects.jsx` are the exception: their image container uses a Tailwind `aspect-[4/3]`/`aspect-[16/9]` class + `object-cover` instead of HTML `width`/`height`, since the bento grid renders each image at a container-relative (not fixed pixel) width — CSS `aspect-ratio` reserves the space for CLS purposes there instead. Project screenshot `<img>`s also use `loading="lazy"` since they're below the fold; the Hero/Navbar/About images don't, since they render above the fold.

**Contact form**: `Contact.jsx` sends messages client-side via EmailJS (`@emailjs/browser`), reading `VITE_EMAILJS_SERVICE_ID`, `VITE_EMAILJS_TEMPLATE_ID`, and `VITE_EMAILJS_PUBLIC_KEY` from `import.meta.env` (see `.env.example`). A local `.env` with real EmailJS credentials is required for the form to actually send.

**Design system ("Refined Dark" / "Refined Light")**: color tokens (`surface`/`surface-raised`, `border`, `fg`/`fg-subtle`/`fg-muted`, `accent`/`accent-hover`) are defined in [tailwind.config.js](tailwind.config.js)'s `theme.extend.colors` as `var(--color-*)` references, NOT literal hex — the actual values live in [src/index.css](src/index.css) as CSS custom properties: a `:root` block (dark, the default) and a `[data-theme="light"]` override block. This means the class names (`bg-surface`, `text-fg`, etc.) never change between themes, only what they resolve to — don't reintroduce literal `purple-*`/`pink-*`/`slate-*`/hardcoded-hex classes for site chrome, and don't add a color that isn't defined in both blocks. `accent-ink` is the one fixed exception — a hardcoded near-black (not a CSS var, doesn't flip with theme) used ONLY for text/icons sitting on an `bg-accent` fill (buttons etc.), since that pairing needs to stay dark-on-amber regardless of theme; using `text-fg` there would break in light mode once `fg` becomes a light color. `font-display` (Newsreader, italic, serif) is for section headings and the Hero name only; body text stays the default `font-sans` (Manrope) set globally in `index.css` — both loaded via the Google Fonts `@import` at the top of that file. The one deliberate exception to the token palette is the carousel/backdrop overlay controls in `ProjectModal.jsx`/`CommandPalette.jsx` and the confetti easter-egg colors, which stay fixed black/white/rainbow regardless of theme since they're not page chrome.

**Theme (dark/light)**: [src/theme/ThemeContext.jsx](src/theme/ThemeContext.jsx) — `ThemeProvider` (wraps the app in `App.jsx`, alongside `LanguageProvider`) holds `theme` (`"dark"` | `"light"`) and sets a `data-theme` attribute on `<html>`, which is what the CSS variables in `index.css` key off; persisted to `localStorage` (`portfolio-theme`), falling back to `prefers-color-scheme` on first visit. **A blocking inline script in `index.html`'s `<head>`** duplicates `ThemeContext`'s initial-theme logic to set `data-theme` before first paint — without it, a returning light-mode visitor would see a flash of dark on every load before React mounts. If you ever change the storage key, default, or fallback logic in `ThemeContext.jsx`, update that inline script to match, or the two will disagree. `useTheme()` (toggle button in `Navbar.jsx`, command in `CommandPalette.jsx`) is available to any component under the provider — no prop drilling needed, unlike the command palette's own open/close state.

**Projects layout**: [Projects.jsx](src/components/Projects.jsx) renders `PROJECTS` in a responsive CSS grid (not a stacked list) with the **first** project (`index === 0`) rendered as a wider "featured" tile (`sm:col-span-2 sm:flex-row`, larger title, a "Current role" badge, and a faint decorative "01" numeral) — this is index-based, not a data field, so reordering `PROJECTS` changes which project is featured.

**Styling**: Tailwind utility classes throughout; no CSS modules or styled-components. Icons come from `react-icons` (multiple sub-packages: `fa`, `fa6`, `si`, `ri`, `bi`, `io5`, `tb`), chosen per-icon rather than a single icon set — always import the specific icon from its sub-package, never a barrel/root import.

**Command palette**: [CommandPalette.jsx](src/components/CommandPalette.jsx) opens on Cmd+K/Ctrl+K (global `keydown` listener) or the "⌘K" button in `Navbar.jsx`, built on [`cmdk`](https://github.com/pacocoursey/cmdk)'s bare `Command` primitive (not `Command.Dialog` — the backdrop/overlay/panel is our own, styled to match the site, reusing the same body-scroll-lock + manual Tab focus-trap pattern as `ProjectModal.jsx`). Styling hooks into cmdk's own DOM attributes (`[cmdk-group-heading]`) and the `aria-selected` attribute cmdk sets on the keyboard-highlighted item — both verified against the installed `node_modules/cmdk/dist/index.mjs`, not just assumed. The Settings group includes both the language toggle and the dark/light theme toggle (`useTheme()`/`useLanguage()`, called directly — no prop drilling). Two easter-egg commands ("🎉 Party Mode" triggering a DIY confetti burst, "✨ Fun Fact" pulling from `FUN_FACTS`) are hidden from the default (empty-query) list via a custom `filter` in `CommandPalette.jsx` — their `value` is prefixed `"secret "`, which the filter treats as score-0 until the search string actually matches part of it. `FUN_FACTS` in `constants/index.js` are genuine unfilled placeholders (not AI-drafted guesses like the project `problemStatement`s were) — there's no way to responsibly invent personal trivia about the user, so those need to be written by hand before they're worth anything.

**Animation (LazyMotion)**: [App.jsx](src/App.jsx) wraps the whole tree in `<LazyMotion features={domAnimation} strict>`. Because of `strict`, every animated element must use `m.x` (e.g. `m.div`, `m.img`) imported as `import { m } from "framer-motion"` — using `motion.x` instead will throw at runtime. `AnimatePresence` (used in `Navbar.jsx` for exit animations) is unaffected and still imported directly from `framer-motion`. `domAnimation` covers transform/opacity animations, gestures (`whileHover`/`whileTap`), and exit animations — if a future component needs `drag` or `layout` animations, the feature set in `App.jsx` needs to change to `domMax` (larger bundle).

**SEO/meta**: [index.html](index.html) hardcodes `<title>`, meta description, canonical URL, and Open Graph/Twitter Card tags against the production domain `https://dhavi-portfolio.vercel.app/` — update these if the domain changes. `public/og-image.jpg` (1200×630) is the social-share preview image; `public/favicon-32.png` and `public/apple-touch-icon.png` are generated from `src/assets/logo.webp`. `public/robots.txt` and `public/sitemap.xml` point at the same domain; since this is a one-page app (no real routes), the sitemap only lists the root URL.
